Description:
The next wave of Supply Chain attacks is brewing in our Build Pipelines (CI/CD), where 0-days and novel attack paths are still waiting to be discovered. In 2024, the XZ compression library compromise was used as a trojan horse to backdoor OpenSSH, thankfully, this was caught early on, but the next time it might go unnoticed for much longer. This talk picks up where we left off last year, and we tell the story of how we went from finding 0-day vulnerabilities in the Build Pipelines of critical Open Source packages to predicting TTPs for the next XZ-like attacks. This time we've adapted MITRE's ATT&CK framework for CI/CD environments. We'll go in depth on how Threat Actors can "Live Off the Pipeline" by abusing legitimate build tools to do their bidding proving why this has become Red Teamer's favorite new soft spot.

The session introduces practical methods for predicting and identifying threats before they materialize by mapping build pipeline tactics to our adapted ATT&CK model. Real-world case studies, based on our forensics of the recent Kong Kubernetes Ingress Controller and Ultralytics YOLOv5 ML library compromises, will demonstrate how adversaries exploit build pipelines, escalate privileges, and can remain undetected long enough to have significant impact.

This session empowers attendees to proactively identify and defend against advanced supply chain attacks, effectively countering adversaries that seek to "Live Off the Pipeline" as demonstrated in the XZ compromise.

## Summary

The talk argues that modern CI/CD build pipelines are a major and insufficiently protected component of the software supply chain. Although web-application security has improved substantially, the speaker characterizes build pipelines as having a comparable security maturity to average PHP web applications from 2005.

The central concern is that CI/CD systems routinely execute code in privileged environments containing secrets, tokens, and signing keys. They also process many untrusted inputs, including pull requests and source-code events. François Proulx therefore describes CI/CD remote code execution as “RCE as a service”: attackers can abuse externally triggered automation to execute code in environments that possess valuable credentials and access to artifact-publication mechanisms.

The talk focuses on attacks against GitHub Actions and similar CI platforms. A typical attack involves a workflow triggered by a risky event, such as `pull_request_target`, combined with insufficient token-permission restrictions, execution of untrusted fork code, vulnerable containers or scripts, exposed secrets, or attacker-controlled build files such as Makefiles. The ultimate objective may be to dump runner memory and exfiltrate secrets. The speaker emphasizes that the same general problems can affect GitLab, Azure DevOps, CircleCI, OpenShift, Travis CI, Jenkins, and other systems whose workflows react to source-control events.

Proulx presents the authors’ research tooling and operational approach. Their Package Supply project was rewritten in Go to improve scalability and extensibility, using the open-source Putin scanner as a core component. The research process was also changed from broadly collecting repositories to curating known entities—such as corporations, governments, universities, nonprofits, and open-source foundations—and then identifying their associated GitHub organizations. This supports more targeted scanning and provides a clearer point of contact for responsible disclosure.

Putin scans GitHub and GitLab repositories using read-only tokens. It discovers and indexes repositories, then applies extensible Rego-based rules. A notable feature is scanning remote stale branches, which can preserve old workflow versions. In particular, stale branches may allow attackers to revive vulnerabilities that were fixed in the main branch when workflows use pull-request-target triggers.

The talk describes two related systems:

1. **Package Supply V3** identifies vulnerable build pipelines, assesses exploitability, and supports responsible disclosure.
2. **Package Threat Hunter** monitors GitHub’s public event stream in near real time and can also ingest enterprise audit logs. It enriches events with vulnerability data and other signals, builds user personas, and identifies activity that may represent pipeline exploitation.

The speaker illustrates the approach through investigations involving the Ultralytics YOLOv5 machine-learning library and the Kong Kubernetes Ingress Controller. In the Ultralytics case, Package Supply identified a workflow vulnerability in August 2024, but the issue was overlooked. The same vulnerability was later used in a compromise involving a Monero cryptocurrency miner. This incident motivated the creation of Package Threat Hunter, which was intended to detect exploitation as it occurs rather than only identify vulnerable configurations in advance.

The authors also developed a pipeline-specific risk-scoring concept, the **Pipeline Vulnerability Scoring System (PVSS)**. It began as an adaptation of CVSS 3.1 but was being reconsidered using ideas from CVSS 4.0. The calculator was not described as complete or publicly released at the time of the talk.

For defensive modeling, the authors adapted the OSC&R open software supply-chain attack reference to focus on tactics, techniques, and procedures relevant to build-pipeline exploitation. They further narrowed the model toward common scenarios in which attackers abuse existing pipeline tools to compromise the final software artifact.

The talk concludes that attackers may only recently have begun exploiting these techniques at scale, creating an opportunity for defenders to identify and mitigate them before they become widespread. However, Proulx acknowledges that the research community may already have missed attacks.

## Key technical ideas

### 1. Treat CI/CD as a privileged attack surface

CI/CD pipelines are positioned between source code and released artifacts. They often:

- Execute code automatically in response to network-triggered events.
- Run with elevated privileges.
- Hold secrets, tokens, and signing keys in memory.
- Publish artifacts to package or container registries.

This combination makes build infrastructure a high-value supply-chain target.

### 2. “Living Off the Pipeline” (LotP)

The main technical concept is **Living Off the Pipeline**: attackers abuse legitimate tools already present in a build workflow instead of modifying the workflow itself or introducing obvious malicious tooling.

Examples include:

- **MkDocs:** An attacker-controlled `mkdocs.yaml` configuration can specify hooks that execute arbitrary Python code.
- **Trivy:** A configurable output template using Go-template syntax can provide limited code execution or enable secret exfiltration.
- **Environment-sensitive tools:** Environment variables or shell behavior can be poisoned to influence later jobs, creating a form of second-order code execution.

The approach exploits the trust that pipelines place in their normal build tools and configuration files.

### 3. Risky workflow triggers and untrusted inputs

The talk identifies workflow events such as `pull_request_target`, `workflow_run`, issues, and issue comments as potentially dangerous because they can expose secrets while processing untrusted code.

A vulnerable workflow may combine:

- A risky trigger.
- Unrestricted or overly broad token permissions.
- Checkout of code from an attacker-controlled fork.
- Use of secrets beyond the default repository token.
- Attacker-controlled Makefiles or other build configuration.
- Unfiltered branch names that may enable command or template injection.
- Vulnerable build containers.
- Persistent self-hosted runners.

### 4. Remote stale-branch exploitation

A distinctive detection idea is scanning old remote branches for vulnerable workflow versions. A workflow vulnerability fixed on the main branch may remain exploitable if an attacker can open a pull request against a stale branch containing the older workflow.

This expands pipeline analysis beyond the current default branch and treats forgotten historical configurations as active attack paths.

### 5. Automated, extensible pipeline scanning

Putin is described as an open-source scanner specialized for build-pipeline vulnerabilities. Its design emphasizes:

- Repository discovery using read-only GitHub or GitLab tokens.
- Automated indexing and scanning.
- Rego-based detection rules.
- A domain-specific rule-writing approach.
- Extensibility through cloning and adapting existing rules.
- Scanning of stale branches.

The research process distinguishes broad, lower-confidence findings from internally validated, higher-confidence findings that include exploitability and valuable secrets.

### 6. Combining static exposure analysis with threat hunting

Package Supply and Package Threat Hunter address complementary problems:

- **Package Supply:** “Is this pipeline vulnerable?”
- **Package Threat Hunter:** “Is someone exploiting a pipeline now?”

Threat Hunter ingests public GitHub events and enterprise audit logs, enriches them with vulnerability and contextual data, applies detection rules, and stores results in a data lake. The system also builds behavioral personas for users interacting with projects.

### 7. Signal reduction at large scale

The described processing pipeline reduces a very large event stream to a manageable set of investigations:

- Approximately 5.5 million public GitHub events per day.
- About 500,000 events after initial filtering.
- Approximately 46 events per day flagged for further attention after enrichment and correlation.

This demonstrates an emphasis on practical triage and reducing false positives rather than merely producing large vulnerability inventories.

### 8. Pipeline-specific risk scoring

PVSS adapts vulnerability scoring to build pipelines. The motivation is that conventional CVSS criteria do not fully represent pipeline-specific properties, such as:

- Whether a workflow exposes secrets.
- Whether an attacker can trigger execution using untrusted code.
- Whether the runner is ephemeral or persistent.
- Whether the pipeline can publish or sign artifacts.
- Whether exploitation can affect downstream consumers.

The speaker stated that the calculator was still being refined and was intended for open-sourcing.

### 9. Adapted ATT&CK/OSC&R modeling

The authors adapt supply-chain attack references to focus on build-pipeline TTPs. Their goal is to prioritize the techniques most relevant to a common scenario:

1. A vulnerable pipeline is identified.
2. The attacker gains execution through existing pipeline behavior.
3. Legitimate build tools are abused.
4. Secrets or privileges are obtained.
5. The final artifact is backdoored or otherwise compromised.

This model is intended to support prediction, detection, and defensive prioritization of XZ-like supply-chain attacks.
