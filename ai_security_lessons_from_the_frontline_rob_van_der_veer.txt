## Summary

This keynote argues that AI security is becoming a central responsibility of security professionals because AI systems are increasingly connected to organizational processes and real-world systems. Rob van der Veer’s central position is not that AI is independently malicious, but that people can harm one another through insecure, poorly governed, or over-trusted AI systems.

The talk combines historical examples, attack scenarios, standardization work, and organizational guidance. Its technical emphasis is on recognizing AI-specific assets and attack surfaces while extending existing security practices rather than creating entirely separate security processes.

A key historical example comes from a police machine-learning system developed in the early 1990s to predict crime patterns and possible criminal careers. Although the system was initially considered useful, later analysis identified systemic bias in police data and, more importantly, a serious data-poisoning risk. An attacker who modified the training database could insert apparently innocuous patterns that caused the model to behave as a hidden backdoor. Because the trigger might not appear in ordinary test data and the trained model contains many numerical weights rather than obvious malicious code, the manipulation could be difficult to detect. The project was ultimately abandoned, illustrating the principle that **risk avoidance can be preferable to attempting to mitigate an unacceptable risk**.

Van der Veer also stresses the importance of acknowledging uncertainty. Security professionals should be able to say “I don’t know” or defer an answer instead of producing an unsupported response, including one generated by an AI system that they cannot properly evaluate. He presents honesty about technical limits as an organizational security requirement.

The keynote describes the **AI Exchange** as a major effort to create an open, shared body of knowledge on AI security. It is presented as approximately 200 pages of material, including a broad threat model, controls, threat-modeling guidance, risk-analysis guidance, and organizational recommendations. The project was developed with approximately 130 experts from academia, startups, and practitioner communities. Van der Veer explains that the material has contributed to or informed standards and educational initiatives, including ISO-related AI-security work and a forthcoming European AI Act harmonized security standard.

The proposed security approach divides AI-related risks into several broad categories:

1. **Conventional security threats** affecting infrastructure, applications, access control, confidentiality, and suppliers.
2. **Input threats**, such as evasion attacks, prompt injection, indirect prompt injection, and attempts to extract sensitive model data.
3. **Supply-chain threats**, involving data suppliers, labeling processes, model developers, model hosts, and deployment channels.
4. **Model-behavior risks**, arising because models can be wrong, manipulated, or unpredictable even when they have not been directly compromised.

The speaker recommends incorporating AI assets into existing information-security management systems, supply-chain processes, governance structures, documentation, testing, and monitoring. He argues against building entirely new parallel processes where existing security and software-engineering practices can be extended.

Another important theme is prioritization. Van der Veer recommends beginning with a broad threat inventory rather than relying immediately on a short list such as a top-ten checklist. Narrow lists are useful for awareness but can create blind spots. After identifying the full set of potentially relevant threats, organizations should filter the list according to the specific system, architecture, exposure, and consequences. Controls should then be selected according to the actual risk and cost rather than applied indiscriminately.

The keynote further emphasizes that AI models should never be fully trusted. Hallucinations and other errors are treated as persistent characteristics rather than problems that will necessarily disappear with larger models. Systems therefore require guardrails that limit the consequences of incorrect or manipulated outputs. In agentic AI, where systems can send emails, open doors, access calendars, or perform other actions autonomously, conventional access-control mechanisms should not be replaced by instructions embedded in prompts. Authorization must remain enforced by dependable security controls outside the model.

Finally, the speaker applies the same principle to AI-assisted software development. Engineers should remain actively involved in coding, review, and modification. If developers become passive while an AI system performs most coding tasks, they may lose the ability to review code, make changes, and identify security problems. Continued human technical engagement is therefore presented as necessary for trustworthy development.

## Key technical ideas

### 1. Avoid unacceptable AI risks instead of assuming they can be mitigated

The police-prediction example demonstrates that some risks are sufficiently covert and consequential that the appropriate control is to avoid deploying the application. This is especially relevant when:

- Training data can be modified
- Backdoors may not appear in test samples
- Model internals are difficult to inspect
- A single poisoning event can influence later operational decisions

### 2. Data poisoning is a supply-chain and model-integrity problem

Training data passes through multiple stages, including:

- Image or data collection
- Expert labeling
- Data engineering
- Model engineering
- Deployment
- External hosting or model distribution

Each stage can provide an opportunity for manipulation. The talk highlights backdoor poisoning, where specially labeled samples cause the model to behave incorrectly when presented with a hidden trigger.

### 3. AI systems contain additional assets beyond ordinary software

The proposed AI-system model includes:

- The model
- The application
- Infrastructure
- Training data
- Input data
- Augmentation data
- External model hosts and suppliers

Augmentation data is especially important in retrieval-augmented generation systems. It allows general-purpose models to use organization-specific documents without retraining the model, but those documents must be protected as sensitive assets.

### 4. Retrieval-augmented generation introduces data-protection concerns

In a retrieval-augmented system, relevant documents are retrieved and inserted into the model’s input along with the user’s question. This creates risks involving:

- Unauthorized access to retrieved documents
- Leakage through prompts or model outputs
- Logging or monitoring by cloud AI providers
- Inadequate enterprise-license or opt-out arrangements

The speaker advises organizations to inspect provider terms and determine whether submitted data is logged or monitored.

### 5. Input attacks create a distinct AI attack surface

The keynote identifies several AI-specific input threats:

- **Evasion attacks:** Inputs are modified so that the model misclassifies them.
- **Prompt injection:** A user inserts instructions intended to alter model behavior.
- **Indirect prompt injection:** Instructions are embedded in third-party data that is later included in a model prompt.
- **Model or data extraction:** Attackers attempt to recover sensitive information through crafted inputs.

Controls for these threats often require collaboration with data scientists because they involve statistical, mathematical, and linguistic properties of the model.

### 6. Use data minimization and obfuscation

The speaker recommends minimizing the data provided to AI systems and removing information that is not necessary for the task. He also emphasizes that AI models may continue to function when data is obfuscated or altered within an acceptable range. This can reduce the consequences of data leakage because the exposed data is less recognizable.

He also mentions adding noise to training data as a possible way for data-science teams to reduce the effect of certain poisoning triggers.

### 7. Reduce reliance on model confidence and output behavior

The talk recommends limiting or removing model-confidence information from APIs where appropriate, since confidence signals may support certain attacks. It also recommends monitoring both:

- Conventional security events, such as access and authentication
- Statistical properties of incoming AI inputs

This requires cooperation between security and data-science teams.

### 8. Apply “zero model trust”

Models should be assumed to be capable of being wrong or manipulated. A model output should not directly trigger a high-impact action without independent checks.

The example given is a voice-controlled vehicle: even if the model interprets “open the trunk,” a rule-based safeguard should prevent the action while the vehicle is moving. Model guardrails should therefore be implemented outside the model’s own reasoning process where possible.

### 9. Extend existing security and engineering processes

Rather than creating separate AI-security bureaucracies, organizations should extend existing:

- Information-security management systems
- Supply-chain-management processes
- Secure software-development practices
- DevSecOps processes
- Governance, risk, and compliance activities
- Documentation and testing procedures

AI-specific assets, suppliers, threats, consequences, and controls should be incorporated into these existing structures.

### 10. Threat modeling should begin broadly, then become selective

Short checklists are useful for awareness but may omit important risks. The recommended process is:

1. Start with a comprehensive threat list.
2. Eliminate threats that do not apply to the system.
3. Identify the smaller set of relevant risks.
4. Select controls based on exposure, architecture, consequences, and implementation cost.

For example, rate limiting may help against repeated model experimentation, but it may be ineffective if an attacker can download a publicly available model and perform attacks offline.

### 11. Indirect prompt injection is an inherent operational risk

A document processed by an AI system may contain hidden instructions that alter the model’s behavior. This can occur when external content is placed into a prompt, such as an application letter submitted to an HR system.

The talk presents mitigation techniques—such as instructing the model to ignore embedded instructions or separating data from instructions—but characterizes the situation as an arms race. Organizations must therefore assess whether the residual risk is acceptable.

### 12. Agentic AI requires conventional security enforcement

Agentic systems can autonomously perform actions and interact with heterogeneous systems. Their behavior may be complex and difficult to predict.

The speaker specifically warns against implementing authorization through prompt instructions such as “only HR users may access personal files.” Such instructions can be manipulated. Access control should instead be enforced using conventional security frameworks and mechanisms external to the model.

### 13. AI-generated code requires active human participation

AI-assisted coding can improve productivity, but excessive delegation may weaken engineering and review skills. Developers should remain engaged in:

- Understanding generated code
- Performing code review
- Making changes manually when necessary
- Preserving the ability to assess security and correctness

The argument is that AI tools cannot be treated as a substitute for engineering competence, especially while AI-generated mistakes remain possible.
