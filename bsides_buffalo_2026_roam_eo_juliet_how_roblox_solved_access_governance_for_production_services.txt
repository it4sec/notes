Description:
Bring-your-own-IAM sounds like an attractive security policy, but in practice it's a euphemism for security debt. Every team rolls their own authorization, ignores access governance, and hopes audits never arrive. Roblox lived in that world for years. While infrastructure IAM has matured (AWS IAM, KMS, VPCs), application-layer access remains a free-for-all. Internal services—admin dashboards, data stores, bespoke tools—reinvent "who can do what" with no shared model for time-bound access, multi-tier approvals, or consistent audit. The industry is starting to name this gap, but almost nobody has built and deployed application-layer access governance across heterogeneous services at scale.

This talk tells the story of RoAM (Roblox Access Manager), a generic access governance platform built to orchestrate requests, approvals, expirations, and recertifications—and then notify downstream policy engines via an interface modeled on OpenID AuthZEN. RoAM does not replace the authorization systems teams already have. It wraps them in a shared governance layer: time-bounded access, approval workflows, centralized audit, and automatic revocation. RIF (RoAM Ingestion Framework) is the continuous data ingestion layer that keeps the authorization graph current, projecting resource ownership from upstream data sources into Guard, Roblox's ReBAC authorization service.

Expect us to cover real incidents, design mistakes, and concrete engineering patterns for turning brittle, bespoke authorization into a reusable access governance layer across services—without forcing a single policy engine or a greenfield rewrite.

## Summary

The presentation describes **RoAM—Roblox Access Manager**, an access-governance platform designed to solve a gap between authorization enforcement and governance for production services.

The authors’ central observation is that Roblox already had many systems capable of enforcing access, including service permissions, groups, AWS IAM, Kubernetes access controls, identity-provider groups, SSH proxies, database procedures, YAML configurations, GitHub workflows, and authorization services. However, these systems handled governance independently—or not at all. As a result, access requests, approvals, expiration, revocation, exceptions, and audit records were fragmented across multiple tools and teams.

RoAM was designed as a **governance layer above existing authorization systems**, rather than as a replacement for them. It provides a common lifecycle for:

1. Requesting access
2. Identifying the appropriate approvers
3. Recording justification and discussion
4. Granting access through the existing enforcement system
5. Applying a time-to-live
6. Expiring or revoking access
7. Maintaining an auditable history

This separation is the presentation’s principal architectural idea: **centralize governance without centralizing enforcement**. Each downstream system continues to enforce authorization according to its own model—such as role-based, attribute-based, or configuration-based access—while RoAM standardizes the surrounding governance process.

The need for RoAM was driven by several operational and security problems. Organizational changes caused access mappings and approvals to break; broad permissions became easier to request than precise permissions; access was not consistently revoked after team changes; and quarterly compliance reviews required extensive manual data collection and reconciliation. The speakers cite more than a thousand orphaned YAML files, some containing broad wildcard permissions, as an example of accumulated access-management debt.

The authors also explain why a conventional identity-governance system was insufficient for production infrastructure. Production access depends on dynamic context, including on-call status, incidents, ownership, environment, risk, compliance scope, and the required access duration. Roblox also manages hundreds of thousands of changing infrastructure objects, such as services, hosts, namespaces, database tables, and other resources. The authors argue that these characteristics require a production-aware governance layer rather than a static group-entitlement model.

RoAM’s data model is intentionally small. Its central entities are access requests, subjects, applications, decisions, and comments. Requests distinguish between the requester and the subject receiving access, allowing users, managers, service owners, groups, service identities, and on-call roles to participate in workflows. Requests include explicit expiration times, and access is ephemeral by default.

Approval decisions are stored separately from access requests. This enables multi-party approval workflows in which resource owners, managers, source-control owners, or other roles can approve independently. Approval rules are treated as data rather than being hard-coded into every workflow. Comments provide an audit thread containing justification, discussion, and review context.

RoAM uses a relational database because compliance and audit questions require joins across requests, applications, decisions, subjects, and comments. Bulk requests are represented as multiple first-class requests linked by a request-group identifier. A transactional outbox is used to persist state changes and publish downstream events reliably without requiring two-phase commit.

The presentation also covers **RIF, the RoAM Ingestion Framework**. RIF continuously ingests organizational and resource data from sources such as databases, HR systems, and storage systems, transforms it, and loads it into an authorization system. Its gRPC service interface supports both traditional pull-based ingestion and event-driven updates. Instead of repeatedly processing an entire large dataset, upstream systems can send changes or deltas when they occur. This keeps the authorization graph current when users change teams, resources change ownership, or organizational structures change.

In the case study, a user requests access to a file owned by another team. RoAM determines the relevant authorization backend and approvers, sends notifications, records the approval process, instructs the backend to grant the permission, and schedules future expiration. If the user later changes teams, RIF updates the authorization graph, causing the previous relationship to disappear and the access to be revoked by the downstream authorization service.

According to the presentation, RoAM produced both security and productivity improvements. The first production customer was an SSH proxy service. The speakers report reducing authorization-call latency from as much as **650 milliseconds to approximately 5 milliseconds** through integration with a more efficient authorization system. They also report replacing standing access with predominantly **four- to eight-hour just-in-time access**, improving compliance-audit and access-review workflows, and reducing duplicated governance work across more than ten teams.

The authors conclude with lessons learned and future work. They would consider using Temporal rather than Kafka for orchestrating ingestion workflows because Temporal would provide workflow execution, communication between steps, and stack traces with less operational complexity. They also identify the value of discovering common access patterns and personas earlier, which could reduce duplication in the authorization graph. Finally, they emphasize designing around user workflows, including Slack, chat, and AI-agent interfaces, rather than assuming that a web UI should be the primary access-request mechanism.

## Key technical ideas

### 1. Governance and enforcement are separate layers

RoAM manages the lifecycle surrounding access but does not replace the authorization engine that ultimately enforces permissions.

- **RoAM owns:** requests, approvals, TTLs, expiration, revocation, notifications, and audit.
- **Downstream systems own:** the actual permission model and enforcement mechanism.

This allows heterogeneous services to participate without rewriting their authorization logic.

### 2. Authorization-backend abstraction

RoAM uses shared backend interfaces to communicate with different authorization systems. The backend may represent a file-storage service, AWS, Kubernetes, a generic authorization service, or another system.

The backend determines how access is enforced, while RoAM uses a common governance process around it.

### 3. Time-bounded and ephemeral access

Every request has an expiration time, and access is intended to be temporary by default. After approval, RoAM schedules an expiration event that later instructs the authorization backend to remove the permission.

This reduces standing access and makes expiration a normal part of the access lifecycle.

### 4. Context-aware and multi-party approvals

Production access may require approval from different roles depending on the resource and situation. RoAM supports multiple decision records for one request, allowing workflows such as approval by:

- Resource owner
- Manager
- Source-control owner
- Other service- or policy-defined approvers

The request advances only when the required approvals are satisfied.

### 5. Flexible subject model

Subjects are polymorphic. They may be:

- Users
- Groups
- On-call rotations
- Service identities
- Other identity-like objects

The separation between requester and target subject also supports requesting access on behalf of another user or group.

### 6. Backend-neutral resource and permission representation

Resource and relation identifiers are stored as strings instead of being forced into one universal permission schema. This enables each authorization backend to preserve its own resource and permission model.

### 7. Relational, audit-oriented data model

RoAM uses a relational database because governance and compliance questions require cross-entity queries. The model includes:

- Access requests
- Subjects
- Applications
- Decisions
- Comments

Comments preserve the rationale and discussion associated with an access request, preventing audit context from being scattered across Slack, tickets, and code-review systems.

### 8. Transactional outbox for reliable event publication

State changes are written transactionally with an outbox record. Downstream events can then be published reliably without requiring distributed two-phase transactions.

### 9. Continuous authorization-graph ingestion

RIF keeps authorization data current by extracting, transforming, and loading information from multiple upstream sources. It supports:

- Periodic pull-based ingestion
- Event-driven delta updates through gRPC

The event-driven approach avoids repeatedly processing large datasets when only a small change has occurred.

### 10. Incremental adoption

Because RoAM does not replace enforcement systems, services can onboard incrementally. Teams retain their existing authorization paths while adopting a shared governance lifecycle.

### 11. Operational lessons about workflow orchestration

The authors initially used Kafka to coordinate distributed ingestion workers but found it difficult to debug and operate. They state that Temporal would have been preferable because it could express extraction, transformation, enrichment, and loading as a workflow and provide execution traces.

### 12. Future direction toward roles, analytics, and agents

The authors identify several extensions:

- Access during outages and infrastructure failures
- Governance of identity-provider groups
- Integration with cloud, Kubernetes, and vault systems
- Service-account access management
- LLM-based access queries and management
- User-behavior analytics for unused-access detection
- Different access policies for AI-agent personas and environments
