Description:
Beyond the buzzword of 'supply chain security,' lies a critical, frequently ignored area: the Build Pipelines of Open Source packages. In this talk, we discuss how we’ve developed a data analysis infrastructure that targets these overlooked vulnerabilities. Our efforts have led to the discovery of 0-days in major OSS projects, such as Terraform providers and modules, AWS Helm Charts, and popular GitHub Actions. We will present a detailed attack tree for GitHub Actions pipelines, offering a deeper analysis than the prior art, and outlining attacks and mitigations. In addition, we will introduce a unique reference for 'Living Off the Pipeline' (LOTP) components, aimed at providing Red and Blue teams with a way to prioritize more risky scenarios.

Benoît Côte-Jodoin is a Senior Product Security Engineer at BoostSecurity researching software supply chain security. Former active CTF player, he now designs challenges for the NorthSec CTF competition.

François is a Senior Product Security Engineer for BoostSecurity, where he leads the Supply Chain research team. With over 10 years of experience in building AppSec programs for large corporations (such as Intel) and small startups he has been in the heat of the action as the DevSecOps movement took shape. François is one of founders of NorthSec and was a challenge designer for the NorthSec CTF.

## Summary

The talk examines a relatively neglected part of software supply-chain security: the build pipelines used to produce open-source software. The authors argue that security programs commonly focus on known vulnerabilities in runtime dependencies, software bills of materials, and malicious packages in ecosystems such as npm, PyPI, and Docker Hub. In contrast, build-time dependencies and CI/CD workflows—particularly GitHub Actions—often receive less scrutiny despite having access to source repositories, release mechanisms, and powerful cloud credentials.

The authors position build pipelines as production-critical systems because they generate artifacts that are later consumed by production environments. They highlight several characteristics that make these pipelines risky:

- Build-time dependencies are often not included in conventional dependency inventories.
- There is a shortage of tools for statically analyzing CI/CD workflows.
- Build tools, compilers, linters, and test tools may contain obscure features capable of triggering code execution.
- Workflows frequently use unsafe defaults, excessive permissions, unverified downloaded scripts, or insufficiently controlled external contributions.
- The GitHub Actions ecosystem contains many thousands of actions but comparatively few published CVEs, which the authors regard as an indication that the area is insufficiently researched rather than inherently secure.

The authors describe an attack pattern involving workflows triggered by pull requests from untrusted contributors. A vulnerable workflow may check out pull-request changes, execute attacker-controlled files, use secrets, or inherit unnecessarily broad GitHub token permissions. Code execution can arise through script injection or through build tools that process attacker-controlled configuration or source files.

To investigate these issues at scale, they developed a data-analysis infrastructure called **Package Supply**. The system clones source repositories, parses CI workflows, applies static-analysis heuristics, produces an inventory of build components, and recursively analyzes relationships among packages and their build dependencies. The authors use BigQuery for large-scale SQL-based analysis and Neo4j for graph analysis, allowing them to evaluate how a vulnerable build component may affect downstream packages.

Their research led to the discovery and responsible disclosure of vulnerabilities in open-source projects, including Terraform providers and modules, AWS Helm Charts, and GitHub Actions. The talk gives particular attention to Terraform modules, whose publication model can make a GitHub repository and its tags directly relevant to registry releases. A compromised workflow in a transitive module dependency can therefore affect users who consume a higher-level module without realizing that the lower-level dependency has changed.

One demonstrated scenario involves a vulnerable Terraform module whose GitHub Actions workflow uses the Go template engine **gomplate**. A pull request can add a `.gomplate.yaml` configuration file using the tool’s `post-exec` feature to execute an arbitrary command in the build pipeline. The attacker can then remove the visible changes, close the pull request, and leave a release tag pointing to a dangling or orphaned commit containing the backdoor. The resulting malicious module can be published without an obvious change in the main branch. In the demonstrated case, the attack could exfiltrate an OpenID Connect credential and enable direct access to a cloud environment using a highly privileged token.

The authors introduce the term **Living Off the Pipeline (LOTP)**, modeled after “Living Off the Land.” The concept covers legitimate build and pipeline tools whose features can be repurposed for malicious execution. They also describe a LOTP reference intended to help red and blue teams identify and prioritize risky pipeline components and scenarios.

As a defensive measure, the authors released **Poutine**, an open-source security scanner focused, at the time of the talk, on GitHub Actions and GitLab. It can scan individual repositories or organizations, including organizations containing hundreds or thousands of repositories, and return findings within minutes according to the presentation. The scanner is intended both for direct pipeline assessment and as part of the authors’ Package Supply analysis.

The authors recommend applying software supply-chain threat modeling to the complete software development lifecycle, inventorying and reducing build dependencies, selecting and maintaining safer dependencies, applying least privilege, explicitly limiting CI/CD permissions, and using static analysis against build pipelines. They emphasize that their current analysis remains relatively shallow and that the research area is still at an early stage, but argue that even simple analysis can uncover serious, exploitable weaknesses.

## Key technical ideas

1. **Build pipelines as supply-chain attack surfaces**  
   CI/CD systems should be treated with the same seriousness as production systems because they create artifacts later used in production.

2. **Build-time dependency inventory**  
   Traditional dependency inventories and SBOM-oriented processes often omit tools used only during building, testing, linting, packaging, or releasing. The authors seek to inventory these direct and transitive build dependencies.

3. **Attack-tree analysis for GitHub Actions**  
   The authors model vulnerable workflows through combinations of:
   - A public repository using GitHub Actions.
   - A dangerous trigger, especially `pull_request_target`.
   - Access to secrets or overly broad default permissions.
   - Checkout or processing of untrusted pull-request changes.
   - Script injection or code-executing build tools.
   - Subsequent theft of credentials or modification of released artifacts.

4. **Static-analysis heuristics at scale**  
   Package Supply parses workflow definitions and applies heuristic checks. BigQuery enables rapid SQL-based analysis across large datasets, while Neo4j represents package and build relationships as a graph.

5. **Recursive build-graph impact analysis**  
   A vulnerability in one build component may propagate through multiple layers of build dependencies. Graph analysis is used to estimate the downstream impact of a compromised action, module, or workflow.

6. **Living Off the Pipeline (LOTP)**  
   LOTP describes abuse of legitimate pipeline tools and features. The example of gomplate’s `post-exec` configuration demonstrates how a normal build utility can become an execution mechanism when it processes attacker-controlled repository content.

7. **Transient or concealed backdooring of releases**  
   The Terraform example shows how an attacker can introduce malicious content through a pull request, trigger a workflow, clean up the visible repository changes, and leave a release tag pointing to a hidden dangling commit.

8. **Credential theft through CI/CD identity**  
   Compromising a workflow can expose secrets or cloud identity tokens. The demonstrated scenario uses an OpenID Connect credential to obtain powerful cloud access outside the Terraform control plane.

9. **Least privilege as a pipeline mitigation**  
   Workflows should explicitly define minimal permissions rather than inheriting broad defaults. The authors identify unspecified GitHub Actions permissions as a recurring weakness.

10. **Poutine security scanner**  
    Poutine is presented as a lightweight, open-source scanner for GitHub Actions and GitLab workflows. It is designed for rapid scanning of repositories and large organizations and reports the classes of workflow weaknesses discussed in the talk.

11. **Research and training infrastructure**  
    The authors also mention a GitHub project called **Muts**, a capture-the-flag environment containing approximately 20 challenges intended to exercise and test detection and exploitation of vulnerable workflows.
